# Work observability — how a context repo self-reports its lingering work

Every context repo — whether it produces ADRs, knowledge, or code — must be **self-aware of the
inconsistencies within it** and expose them through one common operating surface. *The way to
produce is the standard, not the artifact type.* This doctrine defines that way once; the decision
record is [ADR-PA-0003](../adr/ADR-PA-0003-work-observability-contract.md).

Ground truth for why this exists:
[reliever-business #2](https://github.com/papeete-foundry/reliever-business/issues/2) — a generated
gap report that routed to nobody became a noise floor that hid a 28-object hole for a month. A
detector whose output nobody triages is worse than no detector: it trains everyone to ignore red.

## 1. The two layers

Work state in a repo has exactly two layers, mapping the common lifecycle
**detected → triaged → in-progress → resolved**:

| Layer | Authored by | Regenerated by | Examples today |
|-------|-------------|----------------|----------------|
| **Detection ledger** — what the repo's own gates and detectors found wrong | nobody (generated) | CI / tooling on every change | `reliever-business/views/gap-backlog.yaml`, shapes-harness verdicts, `validate_process` output |
| **Kanban** — work a human+agent pair has accepted and is driving | the owning pair, through PRs | never (files are the record) | `reliever-implementation/tasks/` |

The layers connect through **triage**: a human act that turns a detected finding into either a task
file in the repo's own kanban (self-addressed) or a rail-labeled issue in the owner's repo
(cross-context, §5). Detection entries are ephemeral — an entry disappears when the detector runs
clean. Task files are durable — they carry history and close by status.

## 2. `work.yaml` — the root descriptor

Each context repo carries a root `work.yaml` declaring its work surface, so any consumer (a future
dashboard, `papeete-actor check`) reads "what's lingering here" with zero per-repo knowledge:

```yaml
# work.yaml — work-observability surface (ADR-PA-0003)
contract: work-observability/v0
detection:
  - ledger: views/gap-backlog.yaml        # machine-readable, generated — never hand-edited
    generator: tools/report_coverage.py   # what regenerates it
    format: gap-backlog/v1                # producer's schema name, entries per §3
kanban:
  root: tasks/                            # layout per §4
  board: tasks/BOARD.md                   # generated view
```

`knowledge.yaml` stays corpus-only — one descriptor per concern, same discipline as the
kpack/kontract surface split (AGENT-OPERATING-MODEL §7). A repo may declare several detection
ledgers; it must declare at least one, and exactly one kanban.

## 3. Detection entries

The producer and its taxonomy are per-repo; the entry shape is the contract. Every entry carries:

```yaml
- type: MISSING_PROCESS_MODEL             # producer's stable taxonomy
  rail: functional-gap                    # functional-gap | contract-deviation | engineering-debt
  severity: high                          # high | medium | low
  scope: BNK.RLVR.CAP.B2B.001.CRD         # owning capability node — the scoping rule below
  subject: BNK.RLVR.CAP.B2B.001.CRD       # governed artifact id the finding is about
  description: L2 'Dedicated Card Management' has no process/<CAP_ID>/ model
  evidence: ontology/maps/bcm.ttl         # optional — file/report the detector judged from
  resolve: /process                       # optional — suggested skill or tool
```

Identity is `(type, subject)` — that pair is what triage references and what "the entry
disappeared" means. Producers may add fields; they may not omit `rail`, `severity`, `scope`, or
`subject`.

**The scoping rule.** Every finding and every task is owned by exactly one node of the capability
taxonomy, named **explicitly** in `scope` — never left to be inferred from `subject`. The grain
ladder, narrowest level that contains everything the work touches:

| Grain | `scope` value | When |
|-------|---------------|------|
| L2 capability | full id — `BNK.RLVR.CAP.BSP.001.TIE` | the normal case |
| L1 capability | `BNK.RLVR.CAP.BSP.001` | the work crosses L2s within one L1 |
| Zone | `BNK.RLVR.CAP.BSP` | the work crosses L1s within one zone |
| Context (global) | `BNK.RLVR` | the work crosses zones |

Because the ids encode the hierarchy as prefixes, detectors compute this mechanically: the longest
common id prefix over the artifacts involved, truncated to a valid grain. `subject` stays the
precise artifact (a capability, object, or event id); `scope` is where the work *lives* — the
board's grouping key, and the roll-up key for any cross-repo view.

**The gate-block rule.** A membrane gate that blocks per-artifact (a tier gate refusing a
capability, a vendor-pin check failing, a shapes harness rejecting) MUST write a detection entry
carrying the blocked artifact's id and its rail type. A red CI cross with no ledger entry is
non-conformant — that mute red X is precisely the #2 failure mode.

## 4. The kanban

The layout is `reliever-implementation`'s, adopted ecosystem-wide because it already obeys
ledger-as-record (ADR-PA-0002 Decision 5): the task files ARE the ledger; the board is a view.

```
tasks/
  <scope-id>/                   # one directory per owning capability node (§3 scoping rule)
    TASK-001-<slug>.md          # one file per task, YAML frontmatter + body
  BOARD.md                      # generated — never hand-edited
```

Task frontmatter, contract core (repo-specific extras — `epic`, `task_type`, `loop_count` — are
welcome; the contract is a floor, not a ceiling):

```yaml
task_id: TASK-003
scope: BNK.RLVR.CAP.CHN.001.DSH     # owning capability node (§3); capability_id is a conforming alias (implementation legacy)
subject: BNK.RLVR.EVT.CHN.001.DASHBOARD_VIEWED   # optional — the precise artifact, when narrower than scope
bcm_ref: v1.0.0-1-gb06a4af          # provenance pin
status: todo                        # todo | in-progress | done — the ONLY authored states
priority: high                      # high | medium | low
depends_on: []                      # task ids within the same scope, or <scope>/<task_id>
finding_ref: MISSING_PROCESS_MODEL:BNK.RLVR.CAP.CHN.001.DSH   # optional — what triaged into this task, see below
pr_url:                             # set when the PR opens
```

`finding_ref` takes one of two forms. Self-addressed: the `type:subject` identity of an entry in
this repo's own detection ledger — the task closes the loop when that entry regenerates away.
Cross-context: the URL of the mailbox issue in **this** repo that carried the finding in — an
issue opened *by the detecting context's pair* (§5 step 2), so foreign in authorship but always
local in address.

**Authored vs derived states.** Only `todo | in-progress | done` are written into files. Everything
else the board shows — *ready* (deps done), *blocked* (deps not), *needs-info* (unchecked `- [ ]`
under `## Open Questions`), *awaiting-merge* (`pr_url` set, PR open), *stalled* (stall evidence
recorded, e.g. an active `stalled_reason` — not "loop budget exhausted": stalls can occur without
consuming budget) — is computed by the board generator from the record. Nobody hand-maintains a
state machine; the files can't drift from the board because the board is a function of the files.

**The board.** `tasks/BOARD.md` is regenerated by tooling (today `/sort-task` in implementation;
the generator gets extracted into a settler-templated tool so business and design don't fork
dialects). Its grouping key is `scope` — work reads as "what is lingering under this capability
node", at whatever grain the scoping rule assigned. It SHOULD include a **Detected — untriaged**
section fed from the repo's detection
ledgers: every entry with no matching `finding_ref` in any task and no filed rail issue. That
section is the repo's dead-letter queue (AGENT-OPERATING-MODEL §5) — the anti-noise-floor device.
Empty is the healthy state; a standing entry there is a triage debt, visible every time anyone
opens the board.

## 5. Routing and triage — who writes where

The full path of a finding, consistent with the findings rail (§6 of the operating model) and
Autonomy Level 0:

1. **Detect** — automatic. The gate/detector writes the structured entry in its *own* repo's
   detection ledger. No cross-repo write, no token, no bot.
2. **Route** — manual at Level 0. If the finding's rail addresses another context, the detecting
   pair opens a rail-labeled issue in the owner's repo — the mailbox (§5 of the operating model),
   exactly the reliever-business#7/#8 pattern — carrying the entry's `scope` so the owner knows
   which capability node it lands under before reading a word. The ledger entry carries everything
   needed, so this is a copy-paste act; it can become automatable at higher autonomy without changing this
   contract, because the entry already has the full payload.
3. **Triage** — the owner's exclusive act. The owning pair converts the issue (or its own detected
   entry) into a task file in its own `tasks/`, with `finding_ref` for traceability. **Nobody
   authors another context's kanban, not even via PR** — a foreign papeete-actor inserting task files would
   dictate the owner's backlog, breaking boundary-of-knowledge = boundary-of-responsibility.

Self-addressed findings skip step 2: detection entry → own task file.

**Step 2 sends an inter-agent message — rendered, not re-typed.** The mailbox issue is one *binding*
of an [inter-agent message](./INTER-AGENT-MESSAGES.md): a deterministic projection of the detection
entry, not prose a human authors. The finding is the message *payload*; the GitHub issue is one way
to carry it. The detecting pair renders it with `render_message.py` (envelope marker
`finding: {type}:{subject}` for identity/idempotency, `scope` in the title, rail as the label), and
the owner repo's CI runs the envelope-keyed gate `lint_message.py` against
[`https://github.com/papeete-hub/papeete-actor/blob/main/src/papeete_actor/schemas/message.schema.yaml`](https://github.com/papeete-hub/papeete-actor/blob/main/src/papeete_actor/schemas/message.schema.yaml) — skipping its own local issues,
failing any message that dropped its envelope ([ADR-PA-0004](../adr/ADR-PA-0004-inter-agent-message-contract.md)).
reliever-design#3 and reliever-business#14 — prose that dropped the envelope and `severity` — are the
failures this closes.

**Resolution** closes the loop in both layers: the fixing PR merges, the task goes `done`, the
detector regenerates clean and the entry disappears. If the entry survives the fix, the finding
wasn't what the task thought it was — that mismatch is itself a signal, visible on the board.

## 6. Views are consumers, never records

Direction is always **ledger → view**, never back:

- `BOARD.md` — the in-repo view, generated (§4).
- **GitHub issues** — coordination projection and cross-context mailbox; an issue may *precede* a
  task (the mailbox case) but the record of accepted work is the task file it triaged into.
- **Any cross-repo dashboard or Projects board** — an optional consumer that reads each repo's
  `work.yaml` and walks its declared surfaces. Enabled by the contract's uniformity, mandated by
  nothing, authoritative for nothing. Build one when the need appears; it's an afternoon of work
  against a uniform surface, by design. Because business, design, and implementation share the
  same capability taxonomy, `scope` is the cross-repo roll-up key: one tree, every context's
  lingering work hanging under the capability node that owns it.
