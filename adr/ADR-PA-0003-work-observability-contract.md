# ADR-PA-0003 — Work-observability contract — every context repo self-reports its lingering work the same way

> **Moved from `papeete-foundry/ecosystem-governance`, where it was `ADR-ECO-0006`.**
> The decision is unchanged and so is its date — what moved is the repo that owns it
> ([ADR-ECO-0019](https://github.com/papeete-foundry/ecosystem-governance/blob/main/ecosystem/decisions/ADR-ECO-0019-eco-gov-relinquishes-the-contracts.md)
> and [ADR-PA-0014](./ADR-PA-0014-the-agent-doctrine-moves-here.md)). Citations to
> `ADR-ECO-0006` elsewhere in the ecosystem refer to this record.

## Context

Each context repo improvised its own answer to "what work is lingering here": implementation grew
a kanban (`tasks/` + generated `BOARD.md`), business a generated gap backlog
(`views/gap-backlog.yaml`), design a tier gate — same need, three dialects. The cost of leaving it
unstandardized is documented in
[reliever-business #2](https://github.com/papeete-foundry/reliever-business/issues/2): a detector
whose output routed to nobody became a noise floor that hid a 28-object hole for a month. This is
the work-observability slice of the context contract that ADR-ECO-0005 names as follow-up: the way
a context produces and monitors its work is an ecosystem concern; the artifacts it produces are
not.

## Decision

The full doctrine is [`WORK-OBSERVABILITY.md`](../doc/WORK-OBSERVABILITY.md); the decisions:

1. **Two layers, one lifecycle.** Every context repo exposes its work state as a generated
   **detection ledger** (what its own gates found wrong; regenerated by CI, never hand-edited) and
   an authored **kanban** (work its pair accepted; task files in git). Triage connects them:
   detected → triaged → in-progress → resolved.
2. **A root `work.yaml`** declares each repo's detection ledgers and kanban root — the uniform
   entry point that makes any future cross-repo dashboard a pure consumer. `knowledge.yaml` stays
   corpus-only.
3. **Implementation's kanban layout is the norm**: `tasks/<scope-id>/TASK-NNN-<slug>.md` with
   contract-core frontmatter, plus a generated `tasks/BOARD.md`. Task files are the record
   (extends ADR-PA-0002 Decision 5); only `todo | in-progress | done` are authored — every other
   board state is derived by the generator.
4. **Explicit capability scoping.** Every finding and task names its owning capability node in a
   `scope` field — L2 normally; L1 if the work crosses L2s; zone if it crosses L1s; the context id
   if it crosses zones — never inferred from `subject`. The ids encode the hierarchy as prefixes,
   so detectors compute the narrowest containing node mechanically, and `scope` becomes the
   grouping key of every board and the roll-up key of any cross-repo view.
5. **The gate-block rule.** A membrane gate that blocks per-artifact MUST write a structured
   detection entry (rail type, scope, subject id, evidence). A mute red X is non-conformant.
6. **Routing stays on the rail, manually, at Level 0.** Cross-context findings travel as
   rail-labeled issues in the owner's repo (the mailbox), carrying their `scope`; triage into
   `tasks/` is the owner's exclusive act — nobody authors another context's kanban, not even via
   PR. No sync bots, no cross-repo write tokens; the detection entry carries the full payload so
   routing can be automated at higher autonomy without contract change.
7. **Views are consumers.** `BOARD.md`, issues, and any dashboard/Projects board read the ledgers;
   direction is ledger → view, never back; nothing downstream is authoritative or mandated.

## Rationale

- **The way to produce is the standard, not the artifact type** — business ships ADRs, design
  ships contracts, implementation ships code, but "what is lingering and who owns it" is the same
  question everywhere, so it gets one answer (the same split-by-who-consumes-what reasoning as
  ADR-ECO-0001, applied to work state).
- **Generalize the proven, don't invent.** Implementation's kanban already obeys ledger-as-record;
  business's gap backlog is already a generated detection ledger. The contract is the two of them
  named and joined, not a new mechanism.
- **Uniformity buys the big picture for free.** A dashboard over five conforming repos is a loop
  over `work.yaml` files — so it can wait until it's needed, which is the cheapest kind of
  infrastructure. And because every context shares the capability taxonomy, explicit `scope` makes
  that big picture *one tree*: all lingering work, from gap to task, hanging under the capability
  node that owns it — the same structure everything else in the ecosystem already follows.
- **#2's lesson lands as mechanism, not exhortation**: detection is automatic (the gate-block
  rule), triage debt is visible (the board's untriaged section is the dead-letter queue), and
  routing follows the rail that ADR-PA-0002 Decision 4 already fixed.

## Consequences

- Rollout order (details in doctrine §7): this contract lands; then `reliever-implementation`
  (smallest delta — `work.yaml`, structured detection ledger, `scope` alias for `capability_id`),
  then `reliever-business` (gains the kanban; `report_coverage.py` adds the `rail` and `scope`
  fields), then `reliever-design` (gains both; reliever-design#3 triages into its kanban).
- The board generator is extracted from implementation's `/sort-task` into a settler-templated,
  vendor-pinned tool once a second repo needs it.
- The agent card (operating-model §10) gains a **Work surface** row; `charter check` grows a
  conformance check over `work.yaml`; the registry's `implements_contract` (ADR-ECO-0005
  follow-up) gains the work-observability bit.
- Watch for: task-file frontmatter drift across repos (the extracted generator is the natural
  place to validate the contract core), and the untriaged board section silently regrowing a noise
  floor — empty is its only healthy steady state.
